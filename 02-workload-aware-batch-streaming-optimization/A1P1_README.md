# A1P1 - Workload-Aware Cost and Latency Optimization for Hybrid Batch-Streaming Data Architectures in Cloud Environments

**Track:** Track 1  
**Application:** Smart-meter and grid telemetry pipelines in a utility smart grid

This dataset is synthetic, generated by gen_author1.py with seed 2037. It must be described as synthetic in any publication.

## Simulated scenario

A utility runs ~180 ingestion/processing pipelines over AMI smart-meter reads, PMU phasor streams, SCADA feeder telemetry, DER inverter telemetry, outage events and substation alarms. Each pipeline is executed as batch, micro-batch or continuous streaming on a cloud cluster with a given executor configuration, spot share and storage tier. Each row is one hourly window with the workload profile, the configuration, and the resulting p95 latency and cost.

## How it was generated

Ingest rate = per-source base x daily load curve (morning and evening peaks) x seasonal factor x lognormal(0,0.35); 4% of windows have storm alerts that multiply alarm/outage/SCADA rates by 6 and raise burstiness and late events. Latency follows a queueing model: utilisation = rate x (1+0.5 burst) / capacity(executors, vCPU, engine, event size); queue factor u/(1-u) saturating above 0.95, multiplied by mode-specific base latency (window length for batch/micro-batch, checkpoint cost for streaming), storage-tier penalty, late-event and spot-interruption penalties, and lognormal(0,0.4) hidden contention noise with 4% heavy-tail episodes (x1.5-4). Operators pick mode and window from the SLA (tight SLAs mostly streaming), with 30% of windows mis-sized (1.5-3.5x the SLA). Cost = executors x vCPU x region price (+25% at grid peak) x spot discount x mode duty-cycle + memory + tiered storage + storm retry cost, + unobserved egress, with lognormal(0,0.3) noise. Features carry ~5% Gaussian measurement noise, 1-3% missing values in 3 columns and ~0.7% outliers in 2 columns.

## Target / label column(s)

`p95_latency_ms` (regression, log-scale recommended), `cost_usd_per_hour` (regression), `sla_violation` (binary, derived from latency vs SLA; drop `p95_latency_ms` when predicting it).

## Suggested experiments

1. Latency prediction: gradient boosting vs linear model on log(p95_latency_ms); report R2, MAPE.
2. SLA-violation classification from workload + configuration only; report F1, PR-AUC (imbalanced).
3. Cost/latency Pareto: fit surrogate models, then search over (mode, executors, spot_fraction, tier) per workload; compare hypervolume and cost saved at equal SLA attainment vs a fixed always-streaming policy.
4. Robustness: train on 2025, test on 2026 H1 and on storm windows only; report degradation in R2/F1.
